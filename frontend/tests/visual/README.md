# Linux visual regression

Run `npm run test:visual:container` from `frontend/`. The checked-in runner uses Playwright 1.63.0 on Noble Linux amd64 with image digest `sha256:bc6ab0d6d44ff4826e4cb8c1e6d801e185bfc42bb0753f8e2a30efc70db054c7`. The configuration fixes Chromium, locale, time zone, device scale and reduced motion. It starts the application and the existing Storybook server on separate ports.

Use `npm run test:visual:container -- --update-snapshots` to produce candidates. Inspect every changed image and the relevant layout and interaction evidence before committing it. CI compares images with zero differing pixels; it does not approve or update baselines. Screenshots from another operating system are reference material only.

## Coverage

| Suite | Scenarios | Images | Boundary |
| --- | ---: | ---: | --- |
| `platform.spec.ts` | 12 | 24 | Authentication, account profile, user menu, form and nested overlays |
| `stories.spec.ts` | 92 | 92 | 22 public components, plus a loading Button; every representative Story in both themes and widths |
| `surfaces.spec.ts` | 20 | 24 | Home, document editor, Board, Sheet and public reader; Sheet also captures its filter popup |
| `runner.spec.ts` | 3 | 0 | Fresh successful rendering and rejection of real play/render exceptions |

The Storybook cases wait for the current Story's `STORY_FINISHED` event, including `play` and `afterEach`, and reject cached framework play/render errors before preparing a visible state. Storybook 9.1.21 can report a successful finish after catching such an exception, so the status alone is insufficient. Popups are opened explicitly when the Story closed them. The application fixtures are shared with existing UI behavior tests. Home, document editor and reader use real frontend routes; Board and Sheet use real component compositions. The 390px application-surface cases enable touch; the other suites test narrow viewports. All suites wait for the relevant content, fonts and visible images before capturing.

The 24 initial platform images and 96 additional reviewed images below are checked in. The remaining 20 images must be regenerated after their presentation and fixture corrections, then inspected before those suites can pass. A local `--ignore-snapshots` replay only checks the actions and readiness conditions.

## Initial platform snapshots

The 24 `platform.spec.ts` PNGs were generated by [PR #56 CI run 41270462621](https://github.com/singous/orbis/actions/runs/41270462621), artifact `frontend-visual-evidence` (`13068559323`), from source revision `863f0a10b682923fd5fb92a4f159febbd1f29744`. The downloaded ZIP had SHA-256 `0a1b72e24f709b0bc9555b453bbb771dedc44f56ef4ccb3a0b24a09e139e1698`; the images were copied without modification and verified byte for byte.

Each of the following states has light/dark and 1280/390px images: authentication, account profile, user menu, application form, dialog and nested select. All 24 images were inspected for readable content, clipping, overlap, theme material and overlay order. Narrow menus and nested popups remain inside the viewport. These are viewport tests; coarse-pointer behavior has separate UI tests.

These images establish the current platform reference. They do not provide a pixel comparison against the original pre-migration application, certify every business route, or replace keyboard, contrast, screen-reader and database acceptance checks. Changes required by the migration are also assessed with the existing interaction tests and recorded layout comparisons.

## Component and application snapshots

[CI run 41272983539](https://github.com/singous/orbis/actions/runs/41272983539), artifact `frontend-visual-evidence` (`13069309371`), generated all 140 candidates from source revision `837d9b3acfa16f0bd9e2d5de5943a0b9705f93d0`. The ZIP SHA-256 was `02701c0f4c481beee1e64f29c89fa6cc40946dec0bec8ec7fd29d1a8e1c2ad42`. Its 12 existing platform scenarios passed zero-pixel comparison; the other 112 scenarios reported only the 116 missing images.

All 116 new candidates were inspected. The accepted 96 images comprise 76 representative component images and 20 application images: home, document editor, embedded Sheet, Sheet filter and public reader, in each theme and width. They were copied without alteration and verified byte for byte. The embedded Sheet deliberately retains a bounded, scrollable grid viewport; narrow canvas content likewise retains its camera and pan behavior.

The other 20 candidates were held for correction: Sheet's full-height grid stretched its default button; Icons and Badge examples overflowed their narrow theme container; the Popover example lacked focus-ring spacing. Those four component groups account for 16 images. The four Board images also wait for a valid notebook fixture and its loaded navigation state. These candidates are not accepted baselines and must be generated and inspected again after the corrections.
